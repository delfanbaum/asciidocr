= Roadmap

The plan for the next three releases, and some ideas beyond them. Each release
has one theme, a scope, a bar for calling it done, and the decisions it needs
before work starts. Known gaps that aren't scheduled yet live in
`LIMITATIONS.adoc`.

Sizes are rough: *S* (an afternoon), *M* (a few sessions), *L* (needs a design
pass first).

== 0.3: Lists and the known bugs

Theme: empty the README's "Known Bugs" section. Almost everything here is a
parser bug that a writer hits in ordinary prose. The one new language feature
is the document header, which goes into the ASG now so that the 0.4 Python
bindings and DOCX title page can build on it.

=== Lists (L)

The list bugs come from four causes, so they get fixed by reworking how the
parser holds lists rather than one patch each:

. The scanner only recognizes `+* +` and `+. +`: `+**+` scans as a strong span,
  `..` and `...` at the start of a line become an ellipsis (dropping the item),
  and `-`, `1.` and indented markers are text.
. An item's text is attached late: it waits on the inline stack until the next
  item or blank line, then goes to whatever block is on top of the stack by then.
  The reverse also happens: inlines still waiting when a list starts (a heading,
  a paragraph line) are merged into its first item.
. Nothing records which lists are open, so the parser can't nest a list or close
  back to an outer one.
. A blank line closes the list at once, so a later item starts a new list and a
  later `+` has nothing to attach to.

==== Design

Asciidoctor (2.0.17) is the oracle; these rules were checked against it:

* Lists nest by marker identity, not marker length: a marker not already open
  starts a deeper list (`+**+`, `+***+`, then `+*+` is three levels deep), and
  one that is open closes back to its level. `-` under `+*+` nests.
* Blank lines between items don't end a list; the next non-blank line decides.
  An item (with any marker) continues it, anything else ends it.
* `+` attaches the next block to the deepest open item; a blank line before the
  `+` attaches it to the top-level item.
* A block start without `+` (an attribute line, a delimiter, a block title) ends
  the list.
* A delimited block attached to an item has its own list scope, and the outer
  list resumes after it closes.
* A list directly after a description list item (even after a blank line) is
  attached to that item.
* The numeral style of an ordered list follows its marker (`.` arabic, `..`
  loweralpha, `...` lowerroman, `....` upperalpha, `.....` upperroman), not its
  depth.

Decisions:

* The parser gets a separate list context: a stack of open lists (marker, list,
  current item), with one context per open delimited block. Lists stay off the
  block stack until they close, and an item's text is attached to that item as
  soon as its paragraph ends.
* Markers in 0.3: `+*+` to `+*****+`, `-`, `.` to `.....` and `1.`, with or
  without leading whitespace. Lettered (`a.`, `A.`) and roman (`i)`, `I)`)
  markers came later in 0.3, numbered like the dot markers (`a.` like `..`).
* Description lists join the same context, so lists can attach to their items.
  Nested description lists (`;;`, `:::`, `::::`) came later in 0.3: each
  marker is its own list, nested by marker like other lists.
* `List.marker` in the ASG holds the marker as written (`+**+`, `..`, `-`).

Order of work (each step its own commit or PR):

. (Done) A `block_outline` test helper that descends into list items, and
  tests for every case below in `tests/list_tests.rs`; the ones for later steps
  are ignored, with the step in the reason
. (Done) Scanner: the new markers, and list markers before the ellipsis at the
  start of a line
. (Done) Move lists into the list context with today's single-level behavior
  (all existing tests pass), and attach item text as soon as the item's
  paragraph ends. List scopes for delimited blocks came with it
. (Done) Nesting by marker identity
. (Done) Blank lines between items, and the ancestor (blank line, then `+`)
  continuation
. (Done) Description lists in the list context
. (Done) Lists after headings and paragraphs, and headings after list items (`+* a+`
  then `== B` is one item, "a == B", in Asciidoctor)
. (Done) Backends and docs

==== Cases

* [x] Nested lists: `+* parent+` / `+** nested+` (and `.` / `..`), including
  mixed ordered and unordered lists, and shorter markers under longer ones
* [x] `..` and `...` at the start of a line become an ellipsis, losing the
  item's text
* [x] `-` and `1.` markers, and markers with leading whitespace
* [x] A continued item followed by another item (`+* one+`, `+`, `more`,
  `+* two+`) garbles the list
* [x] A continuation that attaches a nested list (`+* parent+`, `+`, `. one`,
  `. two`)
* [x] A continuation, then a blank line, then an item was a hard error ("invalid
  block continuation; no previous block")
* [x] Blank lines between items split the list into several lists
* [x] A blank line, then `+`, attaches to the top-level item (it was a hard error)
* [x] A block attached without `+` (`+* one+`, a `[source]` listing,
  `+* two+`) garbles the list; it should end the list (list, listing, list)
* [x] A delimited block attached with `+` loses the item's text into the block
* [x] `== Head` directly followed by `+* a+` merges the title into the item
  ("Heada")
* [x] A paragraph line followed by `+* a+` (or `Term:: def`) should stay
  paragraph text, as in Asciidoctor (it used to merge into the item, like
  "Heada")
* [x] A heading directly after a list item's text, or after a paragraph line,
  is text (`+* a+`, `== B` is one item; `Text`, `== B` used to be a section
  titled "TextB")
* [x] A list directly after a description list item (`Term:: def`, `+* item+`)
  merges into its text and swallows the next term
* [x] A list after a description list item and a blank line is attached to the
  item
* [x] Description lists: a blank line between items splits the list; a `+` or a
  lazy line after an item garbles the next term (`A:: a`, `more a`, `B:: b` gave
  the term "more aB"); a delimited block without `+` swallows the item's text;
  and a description list after a list item merges into the item's text
* [x] Several terms for one description (`A::` directly followed by `B:: b`):
  Asciidoctor gives one item with two terms, we gave `A` an empty description.
  `DListItem.terms` is now a list of terms (each a list of inlines), as in the
  ASG schema, which changes the JSON output of every description list
* [x] The indentation of a lazy continuation line (`+* one+`, `  more`) is kept
  in the item's text; Asciidoctor strips it
* [x] Asciidoctor-style backend: the ordered numeral style (`arabic`,
  `loweralpha`, ...) from the list's marker
* [x] DOCX: nested lists at their indent level (they were flattened into one
  paragraph). Only the first list in a document had a numbering of its own (and
  it collided with the default one docx-rs writes, so its bullets showed as
  numbers); every list now has its own, ordered ones numbered by marker

The footnote bug that used to be listed here ("a footnote in a list item, when
an earlier footnote exists, moves the item's text") doesn't reproduce in any
backend. The faulty code, `Asg::standardize_footnotes` and the
`extract_footnote*` functions, is only called by its own test; it goes in the
API audit below.

=== Inline and block parser bugs (S–M each)

* [ ] A footnote runs to the last `]` in its paragraph
  (`+A footnote:[plain] here and a stray ] there.+`); close it at the first
  one, as Asciidoctor does
* [ ] The `link:` prefix is output as text; the scanner should recognize the
  `link:` macro name, not only the URL
* [ ] Formatting with a URL inside a link macro mis-nests
  (`+link:x.html[*x http://q.com y*]+`); probably falls out of the `link:` fix
* [ ] An unclosed span before another block still renders as formatting
  (`+a _unclosed text+`, a blank line, `b`), while the same paragraph at the end
  of the file is correctly left as text
* [ ] Apostrophes inside some spans aren't replaced (`+_don't stop_+`, while
  `+*it's here*+` works)
* [ ] CRLF input leaves `\r` in paragraph text: normalize line endings in the
  scanner
* [ ] An ID on an admonition lands on its content, in both the `NOTE: text` and
  the `[NOTE]` + `====` forms
* [x] A paragraph after a `+[[anchor]]+` line gets a leading space
* [ ] A warning for the block macros we don't support (`toc::`, `audio::`,
  `video::`, `[stem]`), which are currently output as plain text without one
* [x] A line of text directly after a section heading (`== Head`, `Text`) is
  merged into the section title ("Head\nText")
* [ ] A line of text directly before or after a delimited listing (`Text`,
  `----`, `x`, `----`, or `----`, `x`, `----`, `more`) is added to the listing;
  it should be a paragraph. (Asciidoctor reads `Text` then `----` as a setext
  section title, which we don't support)
* [ ] A `+` line outside a list stops the conversion after a paragraph ("push_block
  not implemented for LeafBlock") and is dropped after a heading; Asciidoctor
  keeps it as text. `Parser::in_block_continuation` is only reached outside
  lists now, so this can replace it
* [ ] `[verse]` above a paragraph (without a delimited block) is ignored: the
  paragraph stays a paragraph. In the Asciidoctor-style backend, a `[quote]`
  paragraph's text is wrapped in a paragraph `div`, where Asciidoctor has the
  text directly in the `blockquote`
* [ ] Literal paragraphs (a paragraph whose first line is indented) aren't
  recognized; Asciidoctor makes them literal blocks, and attaches one to a list
  item after a blank line (`+* a+`, a blank line, `  literal`)
* [ ] List marker edge cases that differ from Asciidoctor: a tab after the
  marker (`+*<TAB>a+`) isn't an item; six or more dots (`......`) are an
  ellipsis rather than a marker; `+* +` with no text, then `+* b+`, gives
  "* * b" (Asciidoctor: "** b")
* [ ] A `::` line directly after a list item (`+* a+`, `:: b`) drops the text
  after it; Asciidoctor keeps "a:: b" as the item's text
* [ ] A `+` on the last line, with no newline after it, comes out as a backtick
  at the end of the paragraph before it
* [ ] `= Title` after content (`+* a+`, a blank line, `= Title`) stops the
  conversion with an error; Asciidoctor warns and makes it a level 0 section
* [ ] `Parser::preserve_newline_text` is set by the first description list item
  and never unset, so every paragraph after it has its newlines as separate
  inlines in the ASG
* [ ] A single-column table with one cell per line (`|===`, `|a`, `|b`,
  `|===`) fails with "Error creating table"
* [x] A description list term ending its line (`Term::` with the description
  on the next line) doesn't count that newline, so every later location in the
  document is a line too early. The indentation of that next line is also
  kept, where Asciidoctor strips it as it does for other lines of an item's text
* [ ] `C++` in prose (`C++ uses a::b`) comes out as "C``"; Asciidoctor leaves
  it as written
* [x] A bare URL stopped at `-`, `_`, `%`, `~` or `;` (`http://x.com/my-page`
  linked to `http://x.com/my`), and a URL with a non-ASCII character stopped the
  conversion with a panic
* [ ] A one-row table (`|===`, `|a |b`, `|===`) makes that row a header;
  Asciidoctor only makes the first row a header when a blank line follows it
* [ ] `[TIP]` (or another admonition label) above a listing or literal block
  wraps it in an admonition; Asciidoctor ignores the label there
* [ ] A listing's text in the ASG starts with the newline after the opening
  delimiter (`"\ncode\n"`); check against the ASG schema

=== Cross references and section IDs (M)

* [ ] *Decide* where section IDs are generated: in the parser and ASG (changes
  the JSON/TCK output, but HTMLBook, xrefs and DOCX all get them for free) or
  per backend (what the Asciidoctor-style backend does now). The ASG is the
  likelier answer, since an xref to a generated ID can only show the section
  title if the parser knows the ID
* [ ] Xrefs to generated IDs show the section title (not `[_first_section]`) and
  no longer log a warning
* [ ] Custom xref text: `+<<id,custom text>>+`
* [ ] The `idprefix` and `idseparator` attributes, if the IDs move into the
  parser

=== Quality and housekeeping (S)

* [ ] Fuzz the scanner and parser for hangs and panics (truncated inputs, with a
  short timeout per input); each finding becomes a test
* [ ] CLI-level tests of `-b asciidoctor` and `-e`
* [ ] Compare a few more real documents against `asciidoctor -s` and file what
  differs
* [x] Commit `Cargo.lock` (done in 0.2.1)
* [ ] Spec checks against the official AsciiDoc language specification and ASG
  schema, not just the Asciidoctor docs: which blocks may carry a `title`
  (lists, description lists, paragraphs?); whether a blank line may come
  between a `.Title` line and its block; what two title lines in a row should
  do. Each answer becomes a test or a `LIMITATIONS.adoc` entry

=== Library API (M)

* [ ] Audit the public API in `src/lib.rs`: what's `pub` by accident, and what a
  library user actually needs. Tidy it before the 0.4 Python bindings freeze it.
  Known candidates: `Block::is_ordered_list_item` and
  `Block::is_unordered_list_item`, unused since the list context
* [ ] Remove the unused footnote extraction (`Asg::standardize_footnotes`,
  `Block::extract_footnote_definitions` and the list items' `extract_footnotes`),
  and its `LIMITATIONS.adoc` entry
* [ ] Docs on docs.rs good enough to use the crate without reading the source

=== Document header (M)

Parse the header into the ASG; the backends can mostly ignore it for now.

* [ ] Author information and revision information (author line, `:author:`,
  `:email:`, revision line)
* [ ] Document metadata (`:description:`, `:keywords:`)
* [ ] Render the header in the Asciidoctor-style backend (Asciidoctor's
  `#header` details), since it already copies Asciidoctor's document shell

*Done when:* the README's "Known Bugs" is empty (or lists only things
deliberately moved to a later release), every fixed bug has a fixture, a fuzz
run finds no hangs, the public API has been audited, and the header is in the
ASG.

== 0.4: Outside the terminal

Theme: `asciidocr` as something other programs and people use: from Python,
from Word and from a browser, and for documents longer than an article.

=== Python bindings (L)

* [ ] Start from the existing `py03` branch and decide what to keep
* [ ] *Decide* the API surface. A suggested minimum: `parse(str)` returning the
  ASG, `to_html(str, backend=..., embedded=False)` and `to_docx(str, path)`,
  behind a `python` feature
* [ ] Package with `maturin`, build wheels in CI and publish to PyPI
* [ ] Map our errors to Python exceptions that keep the line number

=== Browser playground (S–M)

* [ ] A static page with a text area and live HTMLBook or Asciidoctor-style
  output (and the ASG as JSON), running the parser as wasm in the browser. The
  existing wasm build targets WASI (for a-Shell), so this likely needs a
  `wasm32-unknown-unknown` build with `wasm-bindgen`
* [ ] Host it (e.g., GitHub Pages) and link it from the README; a "copy as bug
  report" button would make it an easy way to report bugs

=== DOCX out of "experimental" (M–L)

* [ ] List continuations and list titles (easier once the 0.3 list work lands)
* [ ] Headers on tables
* [ ] Real footnotes instead of highlighted in-line text
* [ ] Schema element order in the generated XML (`sz` before `rFonts`, `ind`
  before `spacing`), and `rFonts` set for more than `ascii`
* [ ] Check the output in Word, not only LibreOffice, and fix what Word
  complains about
* [ ] Move to a `docx-rs` release that depends on `zip` 9.0.5 or later. 0.4.22
  (the latest as of 0.2.1) needs `zip` 8.x, which is in the range of a critical
  advisory (a parser differential when reading archives). `docx-rs` only writes
  archives, so the risk is low, but the alert stays open until then
* [ ] Put the 0.3 header on the manuscript title page (author, contact details,
  word count: what a publisher or literary journal expects)

=== Document types (M)

* [ ] Parse `:doctype:` into the ASG (`article`, the default, and `book`)
* [ ] Handle the `book` structure: level-0 sections as parts, level-1 sections
  as chapters, and the special section styles (`[preface]`, `[appendix]`,
  `[glossary]`, `[bibliography]`, `[index]`, ...)
* [ ] DOCX: start each chapter on a new page in a `book`
* [ ] Asciidoctor-style backend: the `book` body class and part and chapter
  markup, checked against Asciidoctor

*Done when:* `pip install asciidocr` works on macOS and Linux; the DOCX backend
drops "experimental" from the README and `LIMITATIONS.adoc` and opens cleanly in
Word; the playground is live; and a `book` parses into parts and chapters.

== 0.5: Asciidoctor parity and HTMLBook

Theme: close the gaps between what a typical document uses and what we parse.
The Asciidoctor-style backend's list of known gaps gets short, HTMLBook catches
up with the header and document types, and TCK conformance becomes a number we
track.

=== HTMLBook (M)

* [ ] Render the 0.3 header (title, author and metadata in the HTMLBook
  `<head>` and the title page)
* [ ] Render a `book` the HTMLBook way: `data-type="book"` on the body,
  `data-type="part"` and `data-type="chapter"` sections, and the matching
  `data-type` for prefaces, appendixes, glossaries, bibliographies and indexes
* [ ] Check the output against the HTMLBook specification

=== Blocks (S–M each)

* [ ] Callout lists. *Decide* first: produce `ListVariant::Callout` from the
  parser (it's what the ASG schema has, and both HTML backends need to tell
  callout lists from ordered lists) or drop the variant
* [ ] Table column widths (`cols="3,1,1"`), then column and row spanning (`2+|`,
  `.2+|`), then cell alignment and styles (`a|`, `^`, `>`)
* [ ] `[source]` without a language: the ASG needs to keep the style, so the
  Asciidoctor-style backend can emit `<pre class="highlight"><code>`
* [ ] Checklists (`+* [x]+`, `+* [ ]+`)
* [ ] Description list markers after a space: Asciidoctor makes `Term :: def`
  (and `Term ;; def`) a description list, while we keep it as text (see
  `description_list_mark_not_if_space_before`)
* [ ] Discrete headings (`[discrete]`)
* [ ] The hardbreaks option (`[%hardbreaks]`, `:hardbreaks-option:`), for our
  poet friends who don't want to wrap everything in `[verse]`
* [ ] `pass` blocks with roles

=== Inlines (S each)

* [ ] `+++text+++` inline passthroughs, and `[pass]` as a paragraph style
* [ ] `+ -- +` with thin spaces around the em dash (`+&#8201;&#8212;&#8201;+`),
  as Asciidoctor does
* [ ] Email autolinks and `mailto:`

=== Conformance (M)

* [ ] Research where the
  https://gitlab.eclipse.org/eclipse/asciidoc-lang/asciidoc-tck[AsciiDoc TCK]
  and the language specification stand now: what has been standardized, which
  parts of the ASG schema are stable, and what the TCK actually tests. The
  answer decides how much the next item is worth
* [ ] Run the TCK through the `json` backend in CI, publish the pass count in
  the README, and treat a drop as a regression

*Done when:* the Asciidoctor-style backend's section of `LIMITATIONS.adoc` lists
only admonition icons, HTMLBook renders the header and `book` structure, and
the TCK's status is researched and, if it's ready, its pass count is published.

== Beyond 0.5

Ideas worth keeping, roughly in the order they follow from the releases above.
None of them is a commitment.

EPUB backend:: HTMLBook is most of the way to EPUB 3 XHTML already; what's
missing is the packaging (the OPF, the navigation document, and a spine built
from a `book` document's chapters). Fits the "writers first" target better than
almost anything else here.

Automatic tables of contents:: `:toc:` and `toc::[]`, once section IDs live in
the ASG.

Syntax highlighting:: For source blocks, either built in (e.g., with `syntect`)
or as classes for highlight.js or Prism.

Watch mode:: `asciidocr --watch`, for writing with a live preview.

PDF output:: Without a Ruby toolchain. Two candidate routes: a Typst backend, or
a print-ready CSS theme for our HTML (our own stylesheet, or one built on
`paged.js`) that a headless browser turns into a PDF. The CSS route reuses the
HTML backends we already have.

Full TCK conformance:: The bar for 1.0, along with a stable ASG/JSON output,
depending on what the 0.5 research finds the TCK has standardized.

A linter or language server:: Built on the ASG and the warnings we already log
(unresolved xrefs, unreadable includes, dropped titles), which are most of a
linter already.

== Not currently planned

These match "Not Currently Planned" in `LIMITATIONS.adoc`. Any of them could
come back if the TCK requires them.

Block style shorthand:: `[#id.role]`. `role=` and `+[[id]]+` work fine.

Conditionals:: `ifdef::`, `ifndef::` and `ifeval::`.

STEM and the UI macros:: Equations, and the `kbd`, `btn` and `menu` macros.
